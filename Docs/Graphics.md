## 16. 브라우저 렌더 백엔드 보강

최근 구현 기준으로 보면 Verity 그래픽스는 단일 네이티브 렌더러만 있는 구조가 아닙니다. 공통 렌더 파이프라인 아래에 브라우저 전용 렌더 백엔드가 추가되어 있습니다.

### 16.1 공통 추상화 계층

현재 렌더링 추상화의 기준 타입은 다음과 같습니다.

- `IRenderDevice`
- `RenderProgram`
- `RenderTexture`
- `RenderTarget`
- `RenderMesh`

상위 계층인 `RenderPipeline`, `Shader2D`, `TextureManager`, `UiRenderer`는 이 추상 타입만 의존합니다.

### 16.2 타깃별 구현

네이티브 구현:

- `GraphicsDevice`
- `NativeRenderProgram`
- `NativeRenderTexture`
- `NativeRenderTarget`

브라우저 구현:

- `BrowserRenderDevice`
- `BrowserRenderProgram`
- `BrowserRenderTexture`
- `BrowserRenderTarget`
- `BrowserRenderTextureBuilder`
- `BrowserGraphicsInterop`
- `wwwroot/graphics.js`

즉 현재 그래픽스 구조는 "파이프라인 공통, 디바이스와 리소스 바인딩은 백엔드별 구현"으로 이해하는 것이 맞습니다.

### 16.3 구조적으로 중요한 이유

- 브라우저는 SDL/OpenGL 경로를 직접 사용할 수 없습니다.
- WebAssembly 쪽 C# 코드는 실제 GPU 호출을 JS WebGL 2.0 계층에 위임해야 합니다.
- 이 추상화 덕분에 상위 렌더 파이프라인 로직은 플랫폼별로 다시 작성하지 않아도 됩니다.

---

## 17. WebGL 2.0 셰이더 변환

브라우저 백엔드는 데스크톱 GLSL을 그대로 컴파일하지 않습니다. `BrowserShaderSourceAdaptation`이 프로그램 생성 직전에 WebGL 2.0 / GLSL ES 3.00용 소스로 변환합니다.

### 17.1 주요 변환 규칙

- `#version 330 core` -> `#version 300 es`
- `precision highp float;`
- `precision highp int;`
- `texture2D(...)` -> `texture(...)`
- 일부 `textureSize(...)` 사용식 보정

### 17.2 문서상 해석 변경

기존 그래픽스 문서를 "모든 셰이더는 데스크톱 GLSL 그대로 컴파일된다"는 전제로 읽으면 현재 구현과 맞지 않습니다.  
실제 경로는 다음과 같습니다.

1. 상위 엔진은 데스크톱 GLSL 기준 소스를 작성
2. 브라우저 백엔드가 WebGL 2.0용으로 변환
3. `graphics.js`가 실제 컴파일/링크 수행

즉 웹 전용 셰이더 문제는 렌더 파이프라인만이 아니라, 이 변환 계층도 같이 봐야 합니다.

## 18. 브라우저 전용 배치와 후처리

최근 구현 기준으로 보면 `RenderPipeline`에는 브라우저에서만 의미가 있는 최적화와 분기 경로가 존재합니다.

### 18.1 브라우저 쿼드 배치

`RenderPipeline`은 `_browserQuadVertices`, `_browserQuadIndices`, `_browserBatchTexture` 등을 사용해 브라우저에서 쿼드 배치를 수행합니다.

따라서 현재 문서에서 "배칭이 전혀 없다"는 표현은 더 이상 완전히 정확하지 않습니다.  
정확한 표현은 다음과 같습니다.

- 범용적인 머티리얼/상태 기반 배칭은 아직 제한적입니다.
- 그러나 브라우저 전용 쿼드 배치 경로는 이미 존재합니다.

### 18.2 브라우저 후처리

과거에는 브라우저 fast path에서 후처리를 막고 있었지만, 현재는 웹에서도 `CameraRenderDetail.PostProcess`와 `camera.PostProcess.Enabled`가 켜져 있으면 후처리 경로를 탈 수 있습니다.

다만 다음 제약은 여전히 중요합니다.

- lighting 경로는 브라우저에서 제한됩니다.
- post-process 셰이더는 screen quad 입력을 전제로 해야 합니다.
- sprite style 셰이더와 post-process 셰이더는 입력 uniform 집합이 다릅니다.

## 19. 브라우저 텍스처 바인딩 규칙

최근 웹에서 스타일 셰이더가 적용된 스프라이트가 흰 사각형으로 보이는 문제가 있었고, 이 문제는 브라우저 텍스처 바인딩 캐시 규칙으로 확인됐습니다.

### 19.1 원인

- `BrowserRenderProgram.SetTexture(...)`가 uniform 이름별 텍스처 핸들을 캐시하고 있었습니다.
- 하지만 WebGL 텍스처 바인딩 상태는 프로그램 경계를 넘어 전역 상태의 영향을 받습니다.
- 따라서 같은 uniform 이름이라고 해서 재바인딩을 생략하면, 실제 draw 시점에는 다른 텍스처가 물려 있을 수 있습니다.

### 19.2 현재 규칙

브라우저 구현에서는 텍스처 바인딩을 프로그램 내부 캐시로 조기 생략하지 않습니다.  
즉 스타일 셰이더를 포함한 draw 경로는 매 draw마다 실제 텍스처 바인딩을 다시 수행한다고 보는 것이 맞습니다.

`CameraTextureAsset`은 카메라 출력용 텍스처 에셋 참조입니다. `Verity.Core.TextureAsset`을 상속합니다.

## 24. `RenderPipeline` 카메라 출력 API

`RenderPipeline`에 멀티 카메라 출력을 위한 새 메서드가 추가되었습니다.

### 메서드

| 시그니처 | 설명 |
| :--- | :--- |
| `void RenderCameraOutputs(World world, bool includeWindowOutputs = false)` | 활성 `CameraOutput` 중 `RenderTexture` 대상을 순서대로 렌더. `includeWindowOutputs`가 true면 `Window` 대상도 포함 |
| `bool TryGetCameraOutputTexture(string outputName, out RenderTexture texture)` | 출력 이름으로 렌더된 텍스처를 조회 |
| `bool TryGetTextureAsset(TextureAsset asset, out RenderTexture texture)` | `TextureAsset` 참조에서 텍스처 조회. `.rendertexture` 확장자면 카메라 출력에서, 아니면 파일에서 로드 |
| `void BlitTexture(RenderTexture source, RenderTarget? targetFbo, int w, int h)` | 텍스처를 타겟 FBO에 전체 화면 블릿 |

### 내부 동작

- `CameraOutputTargetHandle`이 출력 이름별로 `RenderTexture`와 `RenderTarget`을 캐시합니다.
- 설정(Width, Height, Filter)이 변경되면 기존 핸들을 폐기하고 새로 생성합니다.
- `Dispose()` 시 모든 카메라 출력 핸들을 함께 정리합니다.

## 25. 멀티 윈도우 렌더링

데스크톱 런타임에서 `CameraOutputTarget.Window`를 사용하면 각 카메라 출력이 별도 네이티브 윈도우에 표시됩니다. 이 기능은 `NativeMultiWindowRenderer`가 담당합니다.

### 동작 방식

1. `CameraSelection.EnumerateActiveOutputs`에서 `Window` 대상을 수집
2. `RenderPipeline`에서 카메라 렌더 결과를 `RenderTexture`에 저장
3. 각 출력에 대해 SDL2 보조 윈도우를 생성하거나 풀에서 획득
4. OpenGL 컨텍스트를 보조 윈도우로 전환하여 블릿
5. 메인 윈도우 컨텍스트를 복원

### `VeritySdl2Window` 보조 윈도우 API

| 메서드 | 설명 |
| :--- | :--- |
| `CreateAuxiliaryWindow(title, width, height, x, y, resizable, visible, bordered)` | 보조 윈도우 생성 |
| `Show()` / `Hide()` | 윈도우 표시/숨김 |
| `SetTitle(string)` | 제목 설정 |
| `SetSize(int, int)` | 크기 설정 |
| `SetPosition(int, int)` | 위치 설정 |
| `SetResizable(bool)` | 크기 조절 가능 여부 |
| `SetBordered(bool)` | 테두리 표시 여부 |
| `PlaceAfter(VeritySdl2Window?)` | 다른 윈도우 뒤에 배치 (그룹 정렬용) |
| `GetWidth()` / `GetHeight()` | 크기 조회 |
| `GetPosition()` | 위치 조회 |
| `GlMakeCurrent(IntPtr)` | OpenGL 컨텍스트 바인딩 |
| `SwapBuffers()` | 버퍼 교체 |

### 윈도우 풀링

- `MultiWindowPrewarmMode.Startup`: 엔진 시작 시 지정 수만큼 윈도우를 미리 생성
- `MultiWindowPrewarmMode.LazyBackground`: 백그라운드에서 점진적으로 풀을 채움
- `MultiWindowPrewarmMode.None`: 필요할 때마다 생성
- 사용자가 윈도우를 닫으면 해당 키는 `_closedByUser`에 기록되어 재사용하지 않음

### 그룹 정렬

- 같은 `WindowGroup`을 가진 윈도우는 포커스 시 `Order` 순서로 함께 정렬됩니다.
- `PlaceAfter` 메서드를 사용해 윈도우 Z-순서를 그룹 단위로 유지합니다.

## 26. 현재 제약 사항

- 멀티 윈도우 렌더링은 데스크톱(네이티브) 런타임에서만 동작합니다. 브라우저 백엔드에서는 별도 윈도우 출력이 불가능합니다.
- `CameraOutputTarget.RenderTexture`는 모든 플랫폼에서 사용할 수 있습니다.
- 보조 윈도우는 메인 윈도우의 OpenGL 컨텍스트를 공유합니다.
- 윈도우 풀 최대 크기는 64개로 제한됩니다.
- 사용자가 닫은 윈도우는 세션 내에서 다시 열리지 않습니다.
